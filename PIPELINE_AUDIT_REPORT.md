# Отчет об аудите дата-пайплайна (NASA FIRMS + Open-Meteo → HDFS), версия 2

> Аудит проведен по текущему состоянию репозитория (ветка `master`, последний коммит `6624cea`).
> Предыдущая версия отчета описывала архитектуру с Kafka + Spark Streaming; **эта архитектура из кода удалена**, поэтому выводы старого отчета частично неактуальны.

## Краткий вердикт (Подойдет ли для собеседования: Да / Нет / Требует доработки)

**Вердикт:** **Требует доработки**

**Обоснование:** Проект заметно вырос по сравнению с предыдущей версией: появилось разделение инфраструктуры на отдельные compose-стеки, два независимых DAG'а извлечения, валидация payload через Spark, попытка сделать retry-ветку и deadline-алерты. Однако пайплайн по-прежнему содержит **критические дефекты корректности данных** (Open-Meteo всегда запрашивает Берлин вместо Байкала), **нерабочие алерты** (`logger` не определен в общих callback'ах), **неидемпотентную публикацию** и **сломанную наблюдаемость** (remote logging в HDFS не работает, локальные логи удаляются). Инфраструктура Kafka и ClickHouse поднята, но пайплайном не используется — это мертвая нагрузка и вводящая в заблуждение архитектура. Для позиции Junior DE проект демонстрирует знакомство с Airflow 3, HDFS, PySpark и Docker, но показывать его как «production-ready» нельзя.

## 2. Технический анализ работоспособности и архитектуры

| Критерий | Оценка (1-10) | Анализ реализации | Комментарий |
|---|---|---|---|
| **Обработка ошибок** | 4 | В DAG'ах есть `retries=3` с экспоненциальным backoff (`default_args.py:8-11`), `AirflowFailException` при отсутствии Variable и ошибках HDFS, проверка Content-Type у Open-Meteo, `mode=FAILFAST` в Spark. | Обработка ошибок **декоративная**: callbacks падают с `NameError` (#1), ветка `except HTTPError` в FIRMS недостижима (#2), при сбое одного спутника падает весь таск (#3), retry-задачи Open-Meteo — копипаста без собственной логики (#4). Нет классификации ошибок (retryable vs permanent), нет backoff на HTTP 429, нет circuit breaker для внешнего моста. |
| **Идемпотентность пайплайна** | 3 | FIRMS пишет с `overwrite=True`; Open-Meteo пропускает уже существующие staging/raw файлы; публикация использует HDFS `rename` (атомарна в пределах ФС). | Идемпотентность **несогласована**: extract пропускает существующий raw, а publish падает, если целевой файл существует (#5). Publish обрабатывает *весь* staging, а не текущую дату (#6). Нет `_SUCCESS`/манифеста, нет временной директории на прогон, нет overwrite-политики. Повторный запуск за прошлую дату может «подмешать» чужие файлы. |
| **Эффективность работы с HDFS** | 5 | Партиционирование по дате, понятная иерархия `/raw/<source>/year=/month=/day=/`, батчевая запись чанками, `hdfs_client.walk`/`rename`. | Много мелких файлов (~16 JSON на день только для Open-Meteo), нет compaction/retention. Валидация и публикация делают полный обход каталога на каждом запуске — O(всех файлов) вместо O(файлов прогона). Remote logging пишет логи в тот же HDFS и ломается на `:` в run_id (#7). Нет сжатия, нет контроля размера файла, нет квот. |
| **Масштабируемость и конфигурируемость** | 4 | bbox, models, пути вынесены в `params` DAG'а; подключения — через Airflow Connections; конфиги Hadoop/Spark/Kafka/ClickHouse разложены по стекам. | bbox продублирован в двух DAG'ах, `requested_params` — в двух местах, список спутников захардкожен. Open-Meteo URL содержит **захардкоженные координаты Берлина** (#9). Нет dev/prod-профилей, нет Airflow Variables для порогов, нет параметра «сколько дней грузить». `max_active_runs=1` при `catchup=True` и 20-минутном прогоне создает очередь на дни. |
| **Надежность (Production-Ready)** | 3 | Есть deadline-алерты, retry, проверка схемы JSON, удаление невалидных файлов, отдельные restart-политики контейнеров. | Нет реального алертинга (только лог, который сам падает), нет healthcheck'ов в compose (кроме `depends_on` init), нет мониторинга/метрик, нет тестов, нет CI. Критичные конфиги не в git (#8). Внешняя зависимость — ручной браузерный мост на хосте разработчика (#10) — не масштабируется и не переживет перезагрузку. |

**Итоговая оценка по разделу 2:** **3.8/10**. Отдельные компоненты работают, но система в целом не обладает свойствами, которые обычно понимают под production-ready.

**Заключение:** По сравнению с предыдущей версией проект стал структурно чище: появились отдельные стеки, два осмысленных DAG'а, валидация через Spark и попытка построить наблюдаемость. Но остались блокеры, которые нельзя показывать на собеседовании как «готовое решение»: данные Open-Meteo фактически не соответствуют заявленному региону, алерты и логи не работают, повторный запуск публикации ломается, а конфигурация не воспроизводится из git. После выполнения этапов 0-3 проект можно уверенно демонстрировать как учебный production-like пайплайн уровня Junior/Strong Junior.
