# Отчет об аудите дата-пайплайна (NASA API -> HDFS)

## Краткий вердикт (Подойдет ли для собеседования: Да / Нет / Требует доработки)

**Вердикт:** **Требует доработки**

**Обоснование:** Проект демонстрирует наличие основных компонентов дата-пайплайна (Airflow DAG, Kafka, PySpark, работа с HDFS), однако имеет критические архитектурные и технические недостатки, которые делают его непригодным для демонстрации на позиции Junior DE в реальном продакшене. Основные проблемы: наличие явных багов (использование переменной до инициализации), пустая schema-файл, отсутствующие файлы README/docstrings в должном объеме, отсутствие идемпотентности, слабая обработка ошибок и полное отсутствие документации проекта.

## 2. Технический анализ работоспособности и архитектуры

| Критерий | Оценка (1-10) | Анализ реализации | Комментарий |
|---|---|---|---|
| **Обработка ошибок** | 3 | В `kafka_utils.py` есть обработка `KafkaConnectionError`, `TopicAlreadyExistsError`, общий `Exception` с raise. В `producer.py` при ошибке запроса к API ловит Exception, логирует, закрывает продюсер и делает `raise`. В DAG есть проверка переменной через `AirflowFailException`/`ValueError`. | Обработка ошибок слишком общая (`except Exception as e:` без классификации). Нет retry-стратегии на уровне продюсера (только на уровне Airflow retries=2). Отсутствует обработка ошибок сети с backoff, нет валидации ответа API (проверка status code, структуры CSV). Нет обработки частичных ошибок (если один спутник упал - весь батч падает). Нет timeout на KafkaProducer.send (только max_block_ms). |
| **Идемпотентность пайплайна** | 2 | В `producer.py` формируется ключ сообщения: `f"{fire['latitude']}_{fire['longitude']}_{fire['acq_date']}_{acq_time_clean}"` - позволяет избежать дублей при повторной отправке в рамках одного батча. | **Критически слабая**. Нет идемпотентности на уровне загрузки в Kafka (at-least-once без дедупликации). Spark Structured Streaming использует `startingOffsets="earliest"` (всегда читает с самого начала топика) + `checkpointLocation` есть, но `availableNow=True` с earliest - при перезапуске может прочитать одни и те же данные повторно и перезаписать партиции. Нет механизма upsert/overwrite по ключу, нет контроля дублей в целевой зоне HDFS. Отсутствует идемпотентность на стороне извлечения (API может вернуть разные данные, нет проверки по дате/объему). |
| **Эффективность работы с HDFS** | 4 | Есть партиционирование `partitionBy("year", "month", "day")` в Spark. Формат Parquet. CheckpointLocation настроен. Используется Yarn в качестве менеджера ресурсов. | Партиционирование реализовано не полностью - в коде Spark Job формируются колонки year/month/day через функции Spark, но в итоговом DataFrame, который пишется как `df_final`, эти колонки нигде не добавляются (см. баг #2 в разделе 3). Нет оптимизаций: нет `repartition`/`coalesce`, нет `mergeSchema`, нет сжатия (codec не указан), нет контроля размера файлов. Path захардкожен. Отсутствует retention/очистка старых партиций. |
| **Масштабируемость и конфигурируемость** | 4 | Параметры вынесены частично (bootstrap_servers, topic в переменные/аргументы). Kafka настроен на 3 реплики (replication_factor=1 в коде - см. ниже). | Много хардкода: URL API, bbox региона, список спутников, пути HDFS, адреса брокеров Kafka, schema path. Чувствительные данные (API токен) берутся из Airflow Variables - правильно, но нет валидации. Конфиги разбросаны по разным файлам. Нет единого конфиг-файла (YAML/env). |
| **Надежность (Production-Ready)** | 2 | Есть retries на уровне Airflow (retries=2, retry_delay=5min), таймауты (requests timeout=30, kafka request_timeout_ms=10000, max_block_ms=5000). | Критически не готово к продакшену. Отсутствуют мониторинг/алерты (только логи). Нет health-check'ов. Нет обработки backpressure в Kafka/Spark. Нет обработки OOM, нет управления ресурсами Spark (только память указана). Отсутствует тестирование (unit/integration). Schema пустая - данные невалидны. |

**Итоговая оценка по разделу 2:** 3/10. Работоспособность отдельных компонентов есть, но надежность и готовность к production - крайне низкая.

## 3. Чек-лист багов, антипаттернов и упущенных элементов

### Критические баги (Blocker)

Код никогда не дойдет до строки 34 в случае отсутствия переменной - но логика нарушена. Также дублируется проверка (строки 30-31 и 35-36). | Критический. После парсинга создается `df_parsed` (строка 36), но в стриме используется `df_final` (строка 38).
